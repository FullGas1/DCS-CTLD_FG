CTLD Menu Manager

Architecture & Design Documentation

System Overview

The CTLD Menu Manager is a singleton-based hierarchical menu system designed to manage complex, dynamic menu structures for DCS World groups. It provides an abstraction layer over the native DCS mission command APIs while adding automatic pagination, error handling, and state management.

Key Components

  • MenuManager: Singleton that manages all group menus globally
  • Menu: Individual menu structure for a single group
  • Node: Single item in the menu tree (submenu or command)
  • Logger: Handles INFO, WARN, ERROR logging

Refresh Algorithm

Refresh Flowchart

User calls: mgr:refreshMenuForGroup(groupId)
↓
Step 1: Validation
Check if menu exists in memory for groupId
↓
Step 2: Clear
Call missionCommands.removeItemForGroup(groupId, nil)
This removes ALL menu items from DCS UI
↓
Step 3: Rebuild
Traverse memory structure recursively
For each submenu: addSubMenuForGroup()
For each command: addCommandForGroup()
↓
Step 4: Pagination
(Happens automatically during rebuild)
If submenu has >10 items, create pages
↓
Step 5: Return
{ success = true, refreshedCount = N }

Pseudo-code

function refresh(groupId)
    -- Validate
    if not menus[groupId] then
        return { success = false, message = "Not found" }
    end
    
    menu = menus[groupId]
    
    -- Clear entire menu
    missionCommands.removeItemForGroup(groupId, nil)
    
    -- Rebuild tree
    count = 0
    for each child in menu.children do
        count += rebuildNode(groupId, {}, child)
    end
    
    return { success = true, refreshedCount = count }
end

function rebuildNode(groupId, parentPath, node)
    if node.type == "submenu" then
        -- Add submenu to DCS
        missionCommands.addSubMenuForGroup(
            groupId, node.name, parentPath
        )
        
        -- Recursively add children
        count = 1
        newPath = parentPath + [node.name]
        for each child in node.children do
            count += rebuildNode(groupId, newPath, child)
        end
        return count
    
    else if node.type == "command" then
        -- Add command to DCS with wrapped callback
        missionCommands.addCommandForGroup(
            groupId, node.name, parentPath,
            wrappedCallback, {}
        )
        return 1
    end
end

Pagination Algorithm

How Pagination Works

Pagination is triggered during the refresh phase when a submenu's children exceed 10 items. The algorithm automatically distributes items across multiple pages.

Example: 15 Vehicles

Before Refresh (Memory)

{
    name = "Vehicles",
    type = "submenu",
    children = [
        { name = "vehicle_1", type = "command" },
        { name = "vehicle_2", type = "command" },
        ...
        { name = "vehicle_15", type = "command" }
    ]
}

During Refresh (Pagination)

Step 1: Count children = 15 (exceeds 10) Step 2: Split items - Items 1-9: Display on page 1 - Items 10-15: Place in "Next Page" submenu Step 3: Create "Next Page" entry children = [ { vehicle_1 }, { vehicle_2 }, ... { vehicle_9 }, { -- Auto-created "Next Page" name = "Next Page", type = "submenu", children = [ { vehicle_10 }, { vehicle_11 }, ... { vehicle_15 } ] } ]

After Refresh (DCS Display)

USER PRESSES F10 → Vehicles Page 1 (Main): 1. vehicle_1 2. vehicle_2 3. vehicle_3 4. vehicle_4 5. vehicle_5 6. vehicle_6 7. vehicle_7 8. vehicle_8 9. vehicle_9 10. Next Page [USER PRESSES: F10 → Next Page] Page 2: 1. vehicle_10 2. vehicle_11 3. vehicle_12 4. vehicle_13 5. vehicle_14 6. vehicle_15 [USER PRESSES: F11 Previous Page] ← DCS handles this

Key Points

  • Pagination is automatic during refresh
  • Developer doesn't need to handle pagination manually
  • DCS automatically provides "F11 - Previous Page" navigation
  • Pagination is recalculated on every refresh
  • Supports unlimited depth (nested paginations)

Singleton Pattern Implementation

Why Singleton?

The Singleton pattern ensures there's only one global MenuManager instance managing all group menus throughout the mission. This prevents accidental creation of duplicate managers and provides a single point of access.

Implementation

MenuManager = {
    _instance = nil  -- Holds singleton instance
}

function MenuManager:getInstance()
    if not self._instance then
        self._instance = self:new()
    end
    return self._instance
end

function MenuManager:new()
    local obj = {
        menus = {},
        nextMenuId = 1,
        logger = createLogger()
    }
    setmetatable(obj, { __index = MenuManager })
    return obj
end

Lifecycle

Phase Event State
1. Load Script loads MenuManager = {}, _instance = nil
2. First Access Call getInstance() _instance created, menus = {}
3. Group Create Call createMenuForGroup() menus[groupId] = new Menu
4. Runtime Modify, refresh menus Menus persist, survive modifications
5. Mission End New mission starts _instance discarded (reset)

Callback Wrapping & GroupId Injection

The Problem

The DCS API signature for commands is: missionCommands.addCommandForGroup(groupId, name, path, func, arg)

When the player clicks the command, DCS calls: func(arg)

But developers need to know which groupId triggered the command. How do we inject this?

The Solution: Wrapper Closure

-- User provides original function and argument
local function myAction(arg)
    local groupId = arg.groupId  -- Need this!
    local userData = arg.userArgs
    print("Group " .. groupId .. " action: " .. userData)
end

-- MenuManager wraps it:
local wrappedFunc = function()
    -- This closure captures the groupId
    local arg = {
        groupId = 42,  -- INJECTED
        userArgs = originalArg
    }
    myAction(arg)
end

-- DCS calls the wrapper (not original):
missionCommands.addCommandForGroup(
    42, "MyCommand", path, wrappedFunc, {}
)

-- Player clicks command → wrappedFunc() → myAction(arg with groupId)

Implementation in MenuManager

function rebuildMenuNode(groupId, parentPath, node)
    if node.type == "command" then
        -- Create wrapper closure
        local wrappedFunc = function()
            if node.functionToCall then
                local arg = type(node.anyArgument) == "table" and node.anyArgument or {}
                -- arg is passed as-is without modification
                
                -- Call with error handling
                local ok, err = pcall(node.functionToCall, arg)
                if not ok then
                    logger:error("Callback failed: " .. err)
                end
            end
        end
        
        -- Register with DCS
        missionCommands.addCommandForGroup(
            groupId, node.name, parentPath, wrappedFunc, {}
        )
    end
end

_lookup Table Optimization

Purpose

The _lookup table provides O(1) path lookups instead of O(n) tree traversal. This is critical for performance when modifying menus during runtime.

Example

-- Without _lookup (slow):
function findNode(path)
    local current = root
    for _, segment in ipairs(path) do
        found = false
        for _, child in ipairs(current.children) do
            if child.name == segment then
                current = child
                found = true
                break
            end
        end
        if not found then return nil end
    end
    return current
end

-- With _lookup (fast):
function findNode(path)
    local pathStr = table.concat(path, ".")
    return _lookup[pathStr]  -- O(1) lookup!
end

Lookup Table Content

_lookup = {
    ["CTLD"] = <ref to submenu CTLD>,
    ["CTLD.Troop Transport"] = <ref to submenu>,
    ["CTLD.Troop Transport.Infantry"] = <ref to command>,
    ["CTLD.Vehicles"] = <ref to submenu>,
    ["CTLD.Vehicles.vehicle_1"] = <ref to command>,
    ...
}

Maintenance

The _lookup table is automatically updated when:

  • New items are added (addSubMenu, addCommand)
  • Items are removed (removeMenuBranch)
  • Menus are reorganized (rebuild operations)

Error Handling Strategy

Three-Level Error Handling

Level 1: Validation at API Boundary

-- Check parameters immediately
function addCommand(path, name, func, arg)
    if not functionToCall or type(func) ~= "function" then
        return { success = false, message = "Invalid function" }
    end
    -- ...
end

Level 2: Path Validation

-- Verify path exists before modification
local parent = self:_findNode(pathTable)
if not parent then
    return { success = false, message = "Path not found" }
end

Level 3: Callback Error Isolation

-- Catch callback errors to prevent menu corruption
local wrappedFunc = function()
    local ok, err = pcall(node.functionToCall, arg)
    if not ok then
        logger:error("Callback failed: " .. err)
    end
end

Logging Levels

Level When Example
INFO Successful operations "addSubMenu: Added 'CTLD' for group 42"
WARN Recoverable errors "Path 'INVALID' not found"
ERROR Critical failures "Callback execution failed in Infantry"

Design Decisions & Rationale

1. In-Memory Tree Structure

Decision: Maintain entire menu tree in memory before applying to DCS.

Rationale: Allows atomic all-or-nothing updates. If refresh fails, entire menu is rolled back.

2. Automatic Pagination During Refresh

Decision: Recalculate pagination on every refresh, not cached.

Rationale: Simplifies dynamic menu updates. Adding/removing items automatically adjusts pagination.

3. Singleton Pattern for Manager

Decision: Single global MenuManager instance.

Rationale: Prevents accidental duplication, provides single point of access, matches DCS single-threaded environment.

4. Return Tables Instead of Exceptions

Decision: All methods return { success = bool, message = string, ... }.

Rationale: Lua 5.1 has no exception handling. Explicit return values are more robust.
